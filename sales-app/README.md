# 営業管理テスト（Zoho Creator アプリ）

`.claude/skills/zoho-creator-app` スキルの手順で作った、試作用の営業管理アプリです。
Creator 側のフォームは text / textarea / number だけで作り、意味づけ（ステージ、日付、真偽値、担当者の関係）はウィジェットの JavaScript で行います。

## できること

| 画面 | 内容 |
|---|---|
| ダッシュボード | 今月の受注額、目標達成率、進行中の案件、加重見込み（金額 × 確度）、今月の受注予定、ステージ別、担当者別、要フォロー（次回アクションの期限切れ・受注予定日の超過） |
| 案件 | ステージ・担当者・キーワードで絞り込み、追加・編集。ステージを変えると標準の確度が入り、受注・失注にすると確定日が入る |
| 顧客 | 追加・編集。編集画面にその顧客の案件と最近の活動を表示 |
| 活動履歴 | 訪問・電話などの記録。顧客を選ぶと、その顧客の進行中の案件だけが選べる |
| 目標（マネージャーのみ） | 月ごと・担当者ごとの目標金額 |
| 担当者（マネージャーのみ） | 担当者マスタ（メールアドレス＝Creator のログインID、権限 manager / member） |

金額は「3000000」「300万」「3,000,000」のどれでも入力できます。「30万円分」のように読めない値は保存しません。

## フォルダ構成

```
sales-app/
├── ds/
│   ├── SalesApp.ds           ← Creator に取り込むアプリ定義（6フォーム・54項目）
│   └── generate_ds.py        ← 上の .ds を生成するスクリプト（手で .ds を直さない）
├── widget/                   ← ウィジェットのソース
│   ├── plugin-manifest.json
│   └── app/widget.html, css/, js/, translations/en.json
├── dist/SalesApp-widget.zip  ← Creator にアップロードする zip
└── verify/flow-test.js       ← 動作検証（モックで主要な操作をすべて通す）
```

| フォーム | 用途 |
|---|---|
| Sales_Staff_Form | 担当者マスタ |
| Sales_Customer_Form | 顧客 |
| Sales_Deal_Form | 案件 |
| Sales_Activity_Form | 活動履歴 |
| Sales_Target_Form | 月次目標 |
| Sales_Log_Form | 操作記録（誰がいつ何を保存したか。ウィジェットは書くだけで読まない） |

## Creator への載せ方

1. **アプリの取り込み**：Creator で .ds ファイルからアプリを作成し、`ds/SalesApp.ds` を選びます。アプリ名は「営業管理テスト」になります。
2. **ウィジェットの登録**：アプリの設定からウィジェットを作成し、`dist/SalesApp-widget.zip` をアップロードします。インデックスページには **`app/widget.html`** を指定します。
3. **ページに配置**：「営業コンソール」ページを編集してウィジェットを置きます。取り込み直後のページは空です。
4. **最初のマネージャー**：ページを開くと「はじめに：管理者の登録」が出ます。氏名を入れて登録すると、ログイン中のアカウントがマネージャーになります。この画面は担当者マスタが空のときだけ出ます。
5. **担当者の登録**：「担当者」タブで追加します。メールアドレスは各自の Creator のログインIDと同じにしてください。担当者マスタに無いアカウントで開くと、案件などのデータは読まずに止まります。

### ローカルで画面を確認する

`widget/app/widget.html` をブラウザで直接開くと、デモモード（架空のデータ）で動きます。
ヘッダーの切替メニューで利用者を替えると、マネージャーと担当者の見え方の違いを確認できます。
デモモードのデータは、そのブラウザの中にだけ保存されます。

Creator の中（iframe の中）で SDK につながらないときは、デモモードにはならず、エラー画面で止まります。
利用者が保存されない画面に入力してしまうのを防ぐためです（確認用に `?demo=1` を付ければデモで動きます）。

## 権限の設定（Creator 側）

> **ウィジェット側の制御は画面の親切であり、守りではありません。**
> 担当者には「目標」「担当者」タブを出さず、案件・活動・目標も自分の分だけを取得させています。
> ただし、この絞り込みは利用者のブラウザの中で決めています。開発者ツールを使えば、同じ SDK で他の人のデータも取得できます。
> **データを守れるのは、Creator 側のプロファイル（権限）とレコードの条件だけです。**

担当者用とマネージャー用にプロファイルを分け、次のように設定します。

| レポート | 担当者（member） | マネージャー（manager） |
|---|---|---|
| 担当者 一覧 | 閲覧のみ（本人確認に必要） | 閲覧・追加・編集 |
| 顧客 一覧 | 閲覧・追加・編集 | 閲覧・追加・編集 |
| 案件 一覧 | 閲覧・追加・編集。**本人の分だけ** | 閲覧・追加・編集 |
| 活動履歴 一覧 | 閲覧・追加・編集。**本人の分だけ** | 閲覧・追加・編集 |
| 月次目標 一覧 | 閲覧のみ。**本人の分だけ** | 閲覧・追加・編集 |
| 操作記録 一覧 | 追加のみ | 閲覧・追加 |

- **削除権限は誰にも付けなくてかまいません。** ウィジェットは削除を使いません。
- **「本人の分だけ」の条件：** レコードの条件で、ログインユーザー（`zoho.loginuser`）と次の項目が一致するものに絞ります。案件は `owner_email`、活動履歴と月次目標は `staff_email` です。これらの項目は、ウィジェットが保存のたびに担当者マスタのメールから書き込みます。
- **`staff_role` は画面の出し分けにしか使いません。** 必ず Creator のプロファイルとそろえてください。`staff_role` を manager にしても、Creator の権限が担当者用なら他人のデータは読めません。この挙動は意図どおりです。

Creator の権限画面の項目名は版によって異なるため、ここには「何を設定するか」だけを書いています。**この権限設定は実際の Creator では未検証です。**

## CSV で初期データを入れるとき

- 関係は **ID の代わりに名前でも入れられます。** たとえば `owner_name` に担当者の氏名、`customer_name` に会社名を入れ、`owner_id` や `customer_id` は空でかまいません。画面では名前から関係を解決し、次に保存したときに ID が入ります。同じ名前が2人以上いる場合は、名前では解決しません。
- 「本人の分だけ」の権限を使うなら、`owner_email` / `staff_email` も入れてください。空のレコードは担当者から見えなくなります。
- **ステージ（`deal_stage`）：** リード / 提案 / 見積 / 交渉 / 受注 / 失注。
- **権限（`staff_role`）：** manager / member。「マネージャー」「管理者」も manager として扱います。
- **日付：** `2026-09-25` のほか `2026/9/25` でも読めます。年月は `2026-09` か `2026/9` です。
- **真偽値（`is_active`）：** `true` / `false`。空欄は「在籍」「取引中」として扱います。
- **確度（`win_prob`）：** 空欄なら、ステージの標準の確度で計算します。

## 検証したこと・していないこと

**確認済み（この環境のブラウザとモックで確認）**

- **スキル付属の検証3本：** すべて通りました。
  - `schema-check.js`：54項目で不一致は0件でした。
  - `sdk-mock-test.js`：通りました。
  - `demo-smoke-test.js`：通りました。
- **`verify/flow-test.js`：** 194項目すべて通りました。モックは .ds のフォーム定義を読み込み、フォームに無い項目・型の違い・camelCase のパラメータ・実績のない形の criteria を送ると即エラーにします。SDK の形は次の2通りを用意し、同じ場面を両方で通しています。
  - **スキルの資料の形：** `init()` あり、`getInitParams()` は同期、`updateRecord`。
  - **Zoho の JS API v2 の資料の形：** `init()` なし、`getInitParams()` は Promise、`updateRecordById`、追加の応答は `result` 配列。

  確認している場面は次のとおりです。
  - マネージャーと担当者の操作
  - 担当者マスタに無いアカウント、在籍なしのアカウント
  - 担当者マスタが空の状態（初回導入）
  - 権限エラーと0件の区別
  - 追加の応答で、全体は成功（3000）なのに中のレコードが失敗している場合
  - iframe の中での接続（`init()` の無い SDK、読み込みが遅れた SDK）と接続失敗（止めた画面に診断情報を出す）
  - デモモード
  - 全画面とモーダルを 375px 幅で表示したときの横スクロール
- **検証自体の確認：** わざと不具合を入れたコピー7種類で、`flow-test.js` が失敗することも確認しました。仕込んだ不具合は次のとおりです。
  - 操作記録に `updated_at` を送る
  - camelCase のパラメータで呼ぶ
  - 真偽値を boolean のまま送る
  - 担当者も絞り込まずに取得する
  - エラーをすべて0件として扱う
  - iframe の中でもデモモードに落ちる
  - 日付をそろえない

**実際の Creator で分かったこと**

- **1回目：** ウィジェットは Creator の中で読み込まれ、SDK（`widgetsdk-min.js`）も動いていました。それでも「Zoho Creator に接続できませんでした（SDK未検出）」で止まりました。
- **原因：** ウィジェットが SDK の有無を `ZOHO.CREATOR.init` があるかどうかで判定していたことです。スキルの資料は `init()` を呼ぶ前提ですが、Zoho の JS API v2 の資料には `init()` が出てきません（v1 では必須）。修正前のコードに `init()` の無い SDK を与えると、同じ画面が再現しました。
- **修正：** SDK の有無は、データ操作の関数（`ZOHO.CREATOR.DATA.getRecords`）で判定するようにしました。`init()` は、あるときだけ呼びます。
- **次に止まったとき：** 止めた画面に、SDK が持っている関数の一覧（診断情報）を出します。その画面を見れば、次の原因が分かります。

**未検証**

- `init()` より先の、本物の SDK での読み書き。モックは資料に書かれた挙動を再現したものです。資料どうしで食い違う点は、どちらでも動くようにしています。
  - 更新の関数名：`updateRecordById` と `updateRecord` の、ある方を使います。
  - `getInitParams()`：同期の値と Promise の両方を受け取れます。
  - 追加の応答：`data` と `result` 配列の両方から ID を読みます。
- 0件以外の SDK エラーの形。権限エラーのコードなどは仮定です。
- 上記の Creator 側の権限設定。

## 変えるとき

```bash
# 1. 項目を変える：ds/generate_ds.py の FORMS と widget/app/js/config.js の FIELD_MAP を両方直す
python3 sales-app/ds/generate_ds.py
node .claude/skills/zoho-creator-app/verify/schema-check.js sales-app/ds/SalesApp.ds sales-app/widget/app/js/config.js

# 2. 動作を確かめる
node sales-app/verify/flow-test.js
node .claude/skills/zoho-creator-app/verify/sdk-mock-test.js sales-app/widget/app/widget.html
node .claude/skills/zoho-creator-app/verify/demo-smoke-test.js sales-app/widget/app/widget.html

# 3. zip を作り直す（plugin-manifest.json が zip の直下に来るように、widget の中で固める）
cd sales-app/widget && rm -f ../dist/SalesApp-widget.zip && zip -r -X ../dist/SalesApp-widget.zip plugin-manifest.json app
```

- **zip を作り直したら：** Creator で登録済みのウィジェットを編集し、新しい zip をアップロードし直してください。インデックスページは `app/widget.html` のままです。
- **取得の上限：** 1レポートにつき 1,000 件までです。上限に達すると、画面に「集計が不完全な可能性があります」と表示します。
- **備考欄の文字数：** 長文を入れる場合は、Creator 側で複数行テキストの最大文字数を大きくしてください。
