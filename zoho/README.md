# 社内申請システム — Zoho Creator 導入パッケージ

「誰が・何を・いつ見たか」を記録することを設計の中心に置いた社内申請・承認ワークフローです。

```
zoho/
├── dist/shanai-shinsei-widget.zip   ← Creator にアップロードする Widget（これが本体）
├── widget/                          ← zip の中身（編集用ソース）
├── ds/
│   ├── shanai_shinsei.ds            ← アプリケーション定義スクリプト
│   ├── forms_fields.csv             ← .ds が通らない場合の手動作成用 項目定義表
│   └── import_Request_Types.csv     ← 申請テンプレート12種の投入用CSV
├── deluge/                          ← サーバー側で動かす Deluge 関数4本
└── README.md
```

## なぜ Creator に載せるのか（HTML単体との違い）

| レイヤ | HTMLファイル単体 | Zoho Creator |
|---|---|---|
| 画面（フォーム・一覧） | ○ 作れる | ○ |
| データベース（全員で同じデータ） | ✕ 各自のブラウザ内 | ○ |
| **権限・記録（誰が何を見たか）** | **✕ 原理的に不可** | **○** |
| 所有（誰が守り、引き継ぐか） | ✕ | ○ |

HTML単体の localStorage は**閲覧者本人の端末の中**にあり、本人が自由に消去・改ざんできます。
つまり「誰が見たか」は、本人以外の誰にも証明できません。
Creator に載せると、証跡はサーバー側に残り、**閲覧した本人が自分の足跡を消せなくなります**。
この 1点だけでも、社内申請システムを SaaS に載せる理由として十分です。

## 閲覧証跡（このシステムの中核）

### 記録する操作

| 操作 | 記録タイミング |
|---|---|
| 詳細閲覧 | 申請を開いた瞬間＋閉じた時（**滞在秒数付き**） |
| 一覧閲覧 | ダッシュボード・一覧・承認トレイを開いた時 |
| 検索 | 検索実行時（**検索条件と結果件数も記録**） |
| CSV出力 | 出力時（件数付き＝持ち出しの証跡） |
| 印刷 | 印刷実行時 |
| アクセス拒否 | 権限のない画面・申請を開こうとした時 |
| 利用開始／ユーザー切替 | セッション開始時 |

### 記録する内容

日時／セッションID／操作者（氏名・所属・権限）／ログインID／操作種別／対象申請番号・件名／
申請区分／**機微度（S・A・B・C）**／申請の所有部署／**他部署からの閲覧か**／滞在秒数／結果件数／端末情報

### 見え方

- **申請詳細の「閲覧者」タブ** — この申請を誰が何回、いつ最後に見たか。他部署からの閲覧には赤いバッジ。
- **自分の申請一覧の「閲覧」列** — 自分の申請が何回見られたかが一目でわかる。
- **ダッシュボード「あなたの申請を閲覧した人」** — 申請者本人が、自分の情報を誰が見たか確認できる。
- **閲覧証跡画面（管理者）** — 全社の記録を検索・CSV出力。以下を自動でフラグ表示：
  - 深夜アクセス（22時〜5時）
  - 他部署の機微度S/A申請の閲覧
  - 1時間に30件を超える大量閲覧
  - 1日3回を超えるCSV出力
  - アクセス拒否の発生

### 改ざん防止（★必ず設定すること）

Creator の権限設定で、**Access_Logs フォームの「編集」「削除」を全ロールで無効**にしてください。
追加のみ許可します。さらに Deluge 関数 `write_access_log` 経由にすると、
`Login_User` をクライアント申告値ではなく `zoho.loginuser`（サーバー側の値）で上書きするため、
なりすましによる証跡の偽装も防げます。

## 導入手順

### 1. アプリを作る

.ds のインポートは、環境によって「アプリの作成中に問題が発生しました」で失敗します。
**まず方法A（CSV取り込み）を試してください。** これが最短で確実です。

#### 方法A：CSV取り込みでフォームを自動生成（推奨・15〜20分）

Creator は CSV を取り込むと、**列見出しから自動でフィールドを作ります**。
`ds/import_csv/` の11ファイルを、ファイル名の番号順に取り込んでください。

1. アプリを新規作成（空のアプリ／名前は「社内申請システム」）
2. 各 CSV を フォームの新規作成 → 「ファイルからインポート」で取り込む
3. **フォーム名を CSV のファイル名（番号を除いた部分）に合わせる**
   例：`02_Employees.csv` → フォームのリンク名は `Employees`
4. 取り込み後、`00_取込手順.csv` を見ながら **ルックアップ項目と選択項目の型を変更**

番号順に取り込むのは、ルックアップの参照先フォームが先に存在している必要があるためです。
サンプル行が2行入っているので、型の確認が済んだら削除してください。

#### 方法B：手動作成（確実・30〜40分）

`ds/forms_fields.csv` の通りに 11フォームを作成します。
**フィールドのリンク名は CSV の通りにしてください**（widget が参照します）。

#### 方法C：.ds をインポート（現状エラーになる）

`ds/shanai_shinsei.ds` は**設計図としては正確**ですが、Creator のパーサに受理される保証がありません。
.ds の文法は Creator 自身がエクスポートしたものが正解なので、次の手順で確実化できます。

1. Creator で**どれでもいいので既存アプリを開き、設定 → アプリケーションIDE → DSファイルのエクスポート**
2. 出てきた .ds を見れば、その環境が受理する正確な文法が分かります

`ds/probe/` に、どこで弾かれるかを切り分けるための最小ファイルを4つ入れてあります。
上から順に取り込んで、どれが通ってどれが落ちるかを見てください（各30秒）。

| ファイル | 検証内容 |
|---|---|
| `probe_1_minimal.ds` | 最小構成（1フォーム・テキスト2項目・コメントなし） |
| `probe_2_types.ds` | 各フィールド型とルックアップ |
| `probe_3_view.ds` | レポート（view）定義 |
| `probe_4_comment_and_ja.ds` | ブロックコメントと日本語の表示名・選択肢 |


#### アプリ名が意図しない名前になる場合

取り込んだアプリが「研修ポータル データ保存」など別の名前になることがあります。
原因は `application` の直後（＝リンク名）に日本語を書いていた点で、現在の .ds では
`application Shanai_Shinsei` + `displayname = "社内申請システム"` に修正済みです。

すでに作ってしまったアプリの名前は、後から変更できます。

1. Creator のホーム画面で、アプリカードの **「✏️ 編集」** をクリック
2. **アプリケーション名** を「社内申請システム」に変更して保存

または、アプリを開いてから **設定 → 全般 → アプリケーション名**。

> **注意**：表示名は変更できますが、**リンク名（URL に出る識別子）は作成後に変更できません**。
> URL まできれいにしたい場合は、正しい名前で新しくアプリを作り直して .ds を取り込み直してください。
> なお、ウィジェットは `ZOHO.CREATOR.init()` が実行中のアプリ文脈を自動で拾うため、
> **アプリのリンク名が何であってもウィジェットの動作には影響しません**。

どちらの場合も次の3点を必ず設定：
- `Route_JSON` / `Form_Data_JSON` / `Field_Schema` / `Route_Rule` は複数行テキストで**最大文字数 64000**
- `Employees.Email` は Creator のログインユーザーと一致させる（自動ユーザー判定に使用）
- `Employees.Manager` を全員分埋める（承認経路の計算に必須）

### 2. レポートを作る

各フォームに対し、`<フォーム名>_Report` というリンク名でレポートを作成します
（例：`Requests` → `Requests_Report`）。widget はこの名前で読み書きします。
名前を変える場合は `widget/app/js/config.js` の `CFG.REPORTS` を合わせて修正してください。

### 3. マスタを投入

1. Departments（10部署）→ 2. Employees（Manager と Roles を必ず設定）→ 3. Vendors → 4. Accounts
5. **Request_Types** ← `ds/import_Request_Types.csv` をインポート（申請テンプレート12種）

### 4. Deluge 関数を登録

設定 → 関数 → 新規作成で、`deluge/` の4本を貼り付けます。

| ファイル | 関数名 | 用途 |
|---|---|---|
| 01_write_access_log.dg | `write_access_log` | 閲覧証跡の書き込み口（REST公開） |
| 02_calc_route.dg | `calc_route` | 承認経路の生成（サーバー側で再計算） |
| 03_act_on_step.dg | `act_on_step` | 承認・却下・差戻し（**権限をサーバーで再検証**） |
| 04_scheduled_escalation.dg | `escalate_overdue` / `weekly_access_audit` | 遅延督促・週次監査レポート |

スケジュール登録：`escalate_overdue` を毎日9:00、`weekly_access_audit` を毎週月曜8:00。

### 5. Widget をアップロード

設定 → ウィジェット → 新規作成 → `dist/shanai-shinsei-widget.zip` をアップロード →
インデックスページに `widget.html` を指定。
その後、ページ `Workflow_Console` を作成し、ページ編集画面でこのウィジェットを配置します。

### 6. 権限（ロール）を設定

| ロール | Requests | Access_Logs | 備考 |
|---|---|---|---|
| 申請者 | 自分の申請のみ | 追加のみ／閲覧は自分の申請に対するもの | |
| 承認者 | 自分が経路上にいる申請 | 追加のみ | |
| 経理 | 経費系の申請 | 追加のみ | CSV出力可 |
| 人事 | 人事・労務系の申請 | 追加のみ | CSV出力可 |
| 管理者 | 全件 | 追加＋閲覧 | **編集・削除は誰にも与えない** |

レコードレベルの条件式（Creator の権限設定）：
```
Applicant == zoho.loginuser の社員レコード
|| ID in (Approvals[Approver == 自分].Request)
```

> **重要**：widget 側の権限制御（`Perm` モジュール）は「画面の親切」です。
> 守りは Creator 側のロールとレコードレベル条件で必ず二重にかけてください。

## 動作モード

widget は起動時に Creator SDK の有無を判定します。

- **接続時** — Creator のレポートを読み書きします（サイドバー下部に「Zoho Creator 接続済」）
- **未接続時** — デモモードで起動し、localStorage 上の疑似データで全機能が動きます

ローカルで `widget/widget.html` をブラウザで開くだけでデモが動くので、
Creator にアップロードする前に画面を確認できます（初回は SDK 判定に約6秒かかります）。

## 実装済みの機能

**ワークフロー** — 金額しきい値による多段分岐（職務権限規程の再現）／合議・或議・回覧／
代理承認（職務代行、期間指定）／差戻し（申請者へ・特定ステップへ）／取下げ・引き戻し／
条件付承認／自動スキップ（申請者＝承認者、承認者不在、重複）／遅延検知とエスカレーション

**申請テンプレート12種** — 稟議書／経費精算／交通費精算／購買申請／支払申請／押印申請／
休暇申請／出張申請／残業申請／入社手続き／退職手続き／契約書レビュー。
テンプレートは Request_Types の JSON なので、**コードを触らずに様式を追加できます**。

**日本の実務** — インボイス登録番号（T+13桁）の検証と未登録事業者の警告／税区分別の自動計算／
和暦表示の切替／印影（承認時に押印アニメーション）／A4縦の稟議書印刷／
仕訳CSV・振込データCSV出力（BOM付きUTF-8）／電帳法の検索3要件（取引年月日・金額・取引先）

**UI** — ライト/ダークモード／375px幅まで対応／キーボードショートカット（`/` `n` `a` `d` `l` `?`）／
外部ライブラリ不使用のSVGグラフ／スケルトンUI／空状態

## カスタマイズの勘所

| やりたいこと | 触る場所 |
|---|---|
| 申請様式を追加 | Creator の `Request_Types` にレコード追加（JSON） |
| 決裁金額の基準を変更 | 同レコードの `Route_Rule` の `when.gte` |
| 機微度の設定を変更 | `config.js` の `CFG.ACCESS.SENSITIVITY` |
| 異常検知のしきい値 | `config.js` の `CFG.ACCESS.ANOMALY` |
| 権限の範囲 | `config.js` の `CFG.PERMISSIONS` ＋ **Creator のロール設定** |
| フォーム/レポート名の変更 | `config.js` の `CFG.FORMS` / `CFG.REPORTS` |
