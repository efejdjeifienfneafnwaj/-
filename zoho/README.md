# 社内申請システム — Zoho Creator 導入パッケージ

「誰が・何を・いつ見たか」を記録することを設計の中心に置いた社内申請・承認ワークフローです。

```
zoho/
├── dist/shanai-shinsei-widget.zip        ← Creator にアップロードする Widget（本番用・データ空）
├── dist/shanai-shinsei-widget-demo.zip   ← 動作確認用（社員20名・申請50件のサンプル入り）
├── widget/                          ← zip の中身（編集用ソース）
├── ds/
│   ├── ShanaiShinsei.ds             ← ★これを取り込めばアプリが丸ごとできる
│   ├── generate_ds.py               ← 上記の生成スクリプト（スキーマ変更時に再生成）
│   ├── import_Wf_Type_Form.csv      ← 申請テンプレート12種の投入用CSV
│   ├── forms_fields.csv             ← 全156項目の一覧
│   └── import_csv/                  ← .ds が使えない場合のフォーム別取り込みCSV
├── deluge/                          ← 任意で入れる Deluge 関数3本
│                                     （※実機未検証）
└── README.md
```

## なぜ Creator に載せるのか（HTML単体との違い）

| レイヤ | HTMLファイル単体 | Zoho Creator |
|---|---|---|
| 画面（フォーム・一覧） | ○ 作れる | ○ |
| データベース（全員で同じデータ） | ✕ 各自のブラウザ内 | ○ |
| **権限・記録（誰が何を見たか）** | **✕ 原理的に不可** | **○** |
| 所有（誰が守り、引き継ぐか） | ✕ | ○ |

HTML単体の localStorage は**閲覧者本人の端末の中**にあり、本人が自由に消去・改ざんできます。
つまり「誰が見たか」は、本人以外の誰にも証明できません。
Creator に載せると、証跡はサーバー側に残り、**閲覧した本人が自分の足跡を消せなくなります**。
この 1点だけでも、社内申請システムを SaaS に載せる理由として十分です。

## 閲覧証跡（このシステムの中核）

### 記録する操作

| 操作 | 記録タイミング |
|---|---|
| 詳細閲覧 | 申請を開いた瞬間＋閉じた時（**滞在秒数付き**） |
| 一覧閲覧 | ダッシュボード・一覧・承認トレイを開いた時 |
| 検索 | 検索実行時（**検索条件と結果件数も記録**） |
| CSV出力 | 出力時（件数付き＝持ち出しの証跡） |
| 印刷 | 印刷実行時 |
| アクセス拒否 | 権限のない画面・申請を開こうとした時 |
| 利用開始／ユーザー切替 | セッション開始時 |

### 記録する内容

日時／セッションID／操作者（氏名・所属・権限）／ログインID／操作種別／対象申請番号・件名／
申請区分／**機微度（S・A・B・C）**／申請の所有部署／**他部署からの閲覧か**／滞在秒数／結果件数／端末情報

### 見え方

- **申請詳細の「閲覧者」タブ** — この申請を誰が何回、いつ最後に見たか。他部署からの閲覧には赤いバッジ。
- **自分の申請一覧の「閲覧」列** — 自分の申請が何回見られたかが一目でわかる。
- **ダッシュボード「あなたの申請を閲覧した人」** — 申請者本人が、自分の情報を誰が見たか確認できる。
- **閲覧証跡画面（管理者）** — 全社の記録を検索・CSV出力。以下を自動でフラグ表示：
  - 深夜アクセス（22時〜5時）
  - 他部署の機微度S/A申請の閲覧
  - 1時間に30件を超える大量閲覧
  - 1日3回を超えるCSV出力
  - アクセス拒否の発生

### 改ざん防止（★必ず設定すること）

Creator の権限設定で、**`Wf_Access_Form` の「編集」「削除」を全ロールで無効**にしてください。
追加のみ許可します。さらに Deluge 関数 `write_access_log` 経由にすると、
`Login_User` をクライアント申告値ではなく `zoho.loginuser`（サーバー側の値）で上書きするため、
なりすましによる証跡の偽装も防げます。

## 添付ファイル（領収書・見積書・請求書）

### 保存のしかた

Creator 側の項目は `text` / `textarea` / `number` しか使わない方針のため、
ファイルは **base64 に変換し、30,000文字ずつに分割**して `Wf_File_Form` に複数レコードとして保存します。
同じ `file_key` を持つレコードを `chunk_index` 順に連結すると元のファイルに戻ります。

| 制限 | 値 | 変更箇所 |
|---|---|---|
| 1ファイルの上限 | 3MB | `config.js` の `CFG.ATTACH.MAX_BYTES` |
| 1申請あたりの点数 | 10点 | `CFG.ATTACH.MAX_FILES` |
| 対応形式 | PDF / JPEG / PNG | `CFG.ATTACH.ACCEPT` |
| 1レコードの文字数 | 30,000 | `CFG.ATTACH.CHUNK_CHARS` |

> Creator の複数行項目の最大文字数に合わせて `CHUNK_CHARS` を調整してください。
> 取り込み後に大きめのファイルで1度試し、保存できる上限を確認することを推奨します。

### 電子帳簿保存法への対応

経費精算・支払申請・購買申請・出張・交通費では、添付時に
**取引年月日・取引金額・取引先**の入力を必須にしています（`CFG.ATTACH.DENSHICHO_TYPES`）。
この3項目は独立した列として保存されるため、Creator のレポート上でも検索できます。

削除しても**レコードは消さず `deleted` を立てるだけ**にしてあります。証跡を残すためです。

### 証跡との関係

添付の取得は「添付DL」として閲覧証跡に記録されます（ファイル名・サイズつき）。
**誰がどの領収書を持ち出したか**が残ります。

## マスタ管理（画面から編集できます）

**管理者ロールでログイン → サイドバー「設定・マスタ」**。社員・部署・取引先・勘定科目を画面から追加・編集できます。
Creator の素のフォームに出る必要はありません。

| マスタ | 編集できる人 | 主な内容 |
|---|---|---|
| 社員 | 管理者・人事 | 氏名／メール／所属／役職／上長／権限／代理人と期間／在籍 |
| 部署 | 管理者 | コード／部署名／上位部署 |
| 取引先 | 管理者・経理 | 登録番号（T+13桁）／適格事業者／**新規の取引先**／初回取引日 |
| 勘定科目 | 管理者・経理 | 科目コード／勘定科目／既定の税区分 |

### 一括登録は「様式を配る」方式です

決まった型で入力してもらうのではなく、**その型そのものを書き出します。**

| ボタン | 出るもの |
|---|---|
| **記入用の様式を書き出す** | 見出し行＋記入例1行。Excel で開いて追記するだけ |
| **現在の登録を書き出す** | 今登録されている内容。直して戻せます（往復可能） |
| **ファイルから取り込む** | ファイル選択、または Excel からの貼り付け |

書き出したファイルには、データの下に**入力のしかたと選択肢が同梱**されます。

```
社員番号,氏名,フリガナ,メールアドレス,所属部署,役職,上長（氏名）,権限,入社日,在籍
S0001,山田 太郎,ヤマダ タロウ,yamada@example.co.jp,第一営業部,一般,佐藤 健太,申請者,2020-04-01,○

■ 入力のしかた
・この行より下は読み込まれません。消さずに残して構いません。
・役職と権限は、下の選択肢から選んで入力してください。
・上長は氏名で書けます。社員番号やIDは不要です。
...
「役職」に書ける値
　社長／本部長／部長／課長／主任／一般
「所属部署」に書ける値（部署マスタに登録済みのもの）
　第一営業部／経理部／…
```

**空行より下は読み込まれない**ので、説明を消す必要はありません。
BOM 付き UTF-8 なので Excel で開いても文字化けしません。

### 取り込む前に結果を見せます

貼り付け／ファイル選択の時点で、確定する前に内容を表示します。

> 取り込める 18件（新規 15件／更新 3件）　取り込めない 4件　権限を自動提案 6件

取り込めない行は**1行ずつ理由つき**で出ます。

| 行 | 理由 |
|---|---|
| 3行目 | メールアドレスが空です |
| 4行目 | このファイルの中でメールアドレスが重複しています（2行目） |
| 5行目 | 役職「係長」は選択肢にありません |
| 6行目 | 部署「存在しない部」が部署マスタにありません |

### 入力を間違えないための工夫

- **上長は氏名で書けます** — 社員番号やIDは不要。同じファイル内で後に出てくる人も解決されます
- **権限は空欄でOK** — 役職と所属から自動提案します（課長以上→承認者、経理部→経理、人事部→人事）
- **同じファイルを再度取り込むと更新になります** — メールアドレスで既存を判定するので、重複して増えません
- 見出しが違うファイルは、**どの列が足りないか**を示して拒否します
- 記入例の行は自動で除外されます
- 取り込み結果は操作証跡に残ります

### 登録の不足をその場で示します

社員一覧の下に、承認経路が組めない原因になる不足を出します。

| 検出 | 影響 |
|---|---|
| 上長が未設定 | 「申請者の上長」が解決できません |
| メールが未設定 | ポータルからログインできません |
| **メールが重複** | 誰が見たか・誰が承認したかを区別できません |
| 所属が未設定 | 部署による閲覧制御と経路解決が効きません |

該当者の氏名がボタンになっていて、**押すとその人の編集画面が開きます**。
承認経路の「全社員で診断」の結果からも、同じように直接開けます。

### 変更は証跡に残ります

マスタの変更は**変更前と変更後の全項目**が操作証跡に記録されます。
「いつ誰が誰の役職・上長・権限を変えたか」を後から説明できます。

追加した部署や取引先は、**その場で承認経路の選択肢に反映されます**（保存し直す必要はありません）。

## 承認経路の設定（管理者向け）

JSON を書く必要はありません。**管理者ロールでログイン → サイドバー「承認経路の設定」**から画面で設定します。

### 1ステップに設定すること

| 項目 | 内容 |
|---|---|
| ステップ名 | 「部長決裁」など |
| 種類 | 承認（1人）／合議（複数人）／或議（誰か1人）／回覧（確認のみ） |
| 承認するのは誰か | 申請者の上長／役職で指定／部署で指定／特定の人を指名／申請者が選ぶ |
| 何人の承認で次へ | 合議のとき。全員／N人／N%（例：5人中3人） |
| 標準処理日数 | この段に回ってきてからの日数。超えると遅延表示 |
| 通す条件 | 下記の条件ビルダーで指定 |

「特定の人を指名」は選べますが、**異動・退職のたびに経路を手で直す必要がある**旨の警告が出ます。役職や部署での指定を推奨します。

### 条件は AND / OR と入れ子で組めます

`申請金額が10万円以上 かつ （区分が設備投資 または 至急扱いがチェックされている）` のような条件を、
項目・比較方法・値のプルダウンで組み立てます。**条件の数に上限はありません。**
組んだ条件はその場で日本語の文章になって表示されるので、設定を読み違えません。

金額は「300000」でも「300,000」でも「**30万**」でも入力でき、入力中に `＝¥300,000` と円換算が出ます。
数値として読めない入力（「30万円分」など）は**確定できません**。

**条件に使える項目**

| 種類 | 例 |
|---|---|
| 組み込み | 申請金額／申請者の所属部署／申請者の役職／明細の行数／添付ファイルの数 |
| 取引先の状態 | 適格請求書発行事業者でない取引先を含む／新規の取引先を含む |
| **明細行の集約** | いずれかの行の勘定科目／すべての行の取引先／合計金額／最大金額／該当する行数 |
| 申請区分の各項目 | その様式で定義されている入力項目すべて |

明細行が条件に使えるため、「**取引先が新規なら法務の確認を追加**」「**勘定科目が接待交際費なら経理部長**」
といった、日本の経費ワークフローで最も多い要件をそのまま書けます。

### 期限を過ぎたときの扱い

段ごとに指定できます。

| 設定 | 動き |
|---|---|
| 何もしない | 画面に遅延として表示されるだけ |
| 本人に督促を送る | 承認者本人に通知 |
| 本人と上長に督促を送る | 両方に通知。承認できるのは本人のまま |
| **上長も承認できるようにする** | 期限を過ぎると承認者の上長にも権限が広がる |

**自動承認は実装していません。** 承認の事実が無いまま承認済にすると証跡としての意味が失われるためです。
滞留の解消は「権限を広げる」ことで行い、誰が押したかは必ず残ります。
権限が広がって回ってきた申請には、承認画面に「本来の承認者の期限超過により承認できる状態です」と明示されます。

### 保存する前に試せます

これが他社製品にほとんど無い機能です。

- **経路テスト** — 申請者と金額を入れると、**実際に解決された承認者の氏名**で流れを表示します。
  「部長」ではなく「鈴木 由美（第一営業部 部長）」まで出ます。
- **全社員で診断** — 在籍者全員 × 条件のしきい値を総当たりして、経路が成立しないケースを一覧にします。
  「承認者が決まらない」「誰の承認も経ずに完了してしまう」を**保存前に**発見できます。
  症状ごとに直し方（社員マスタで上長を設定、など）も表示します。

### 保存できない設定は止まります

- 存在しない項目を指す条件、値が空の条件、承認者が未設定のステップは**保存を拒否**します
- 存在しない項目を指していた条件を申請金額として扱った場合は、その旨を警告します
- 「全社員で診断」の結果、承認者が1人も決まらない社員がいる場合は警告します

### 保存する前に、何がどう変わるかを見せます

決裁基準の変更は稟議規程の改定そのものなので、無言では確定させません。

- **ステップの変更** — 追加／削除／変更を項目ごとに列挙（条件は変更前後の日本語で）
- **金額帯ごとの決裁者** — 変更前と変更後を並べ、**決裁の段数が減る金額帯は赤で警告**
- 進行中の申請には適用されない旨を明示

変更前の定義は操作証跡に残ります。

### 進行中の申請は影響を受けません

申請時に承認経路のスナップショットが申請レコードに焼き込まれるため、
**経路を変更しても、すでに動いている申請は従前の経路で最後まで流れます。**

## 最初に開いたとき（初回セットアップ）

本番用の zip には、**サンプルデータが1件も入っていません**。そのままだと社員マスタが空で、
誰のメールアドレスとも照合できず、誰もログインできません。そこで社員が0件のときだけ、
**いま開いている人を最初のシステム管理者として受け入れる画面**が出ます。

1. 氏名・部署・役職を入れて「この内容で始める」
   （メールアドレスはログイン中のものが自動で入ります）
2. 管理者パスワードを決める
3. あとはマイページに「セットアップの続き」が出続けます

| 項目 | 内容 |
|---|---|
| あなたを登録する | 最初のシステム管理者。1で完了します |
| 部署を登録する | 社員の所属と承認経路は部署名で紐づきます |
| 社員を登録する | 「記入用の様式を書き出す」→記入→「ファイルから取り込む」が早いです。1人ずつ追加もできます |
| 管理者を2人以上にする | 1人だとその人の異動・退職で誰も設定を変えられなくなります |
| 勘定科目を登録する | 空だと経費精算・購買申請の明細が入力できません。標準の20科目をその場で入れられます |
| 承認経路を確かめる | 全社員 × 全金額帯で、承認者が決まらない人がいないかを診断します |

### 社員マスタが整うまでのあいだ

役職や上長が未登録だと、承認者が1人も決まらない申請区分が出ます。
そのまま段を消すと、誰の決裁も経ないまま承認済になってしまうため、
**生きた承認段が1つも残らない場合に限り**、システム管理者を暫定の承認者に立てます。

- 経路と申請画面に「暫定でシステム管理者（◯◯）が承認します」と出ます
- 自動承認は行いません。必ず本人が承認ボタンを押し、その記録が残ります
- 社長のように上長がいない人は、部下を承認者にせず自己決裁として扱います
- 社員がまだ1人しかいない状態では「自己承認」として明示したうえで通します
- 暫定の状態は「成立」ではないため、全社員診断・保存前チェック・セットアップの進捗の
  いずれも**未完了**として数えます。社員マスタを整えると自動で本来の承認者に戻ります

## 導入手順

### 1. アプリを作る（.ds を取り込むだけ）

Creator → アプリケーション → 新規作成 → **「ファイルからアプリを作成」→ `ds/ShanaiShinsei.ds`**

この .ds は、**Creator が実際にエクスポートした .ds の文法に合わせて生成**してあります
（推測ではなく、動作実績のある LMS アプリの .ds を見本にしています）。
11フォーム・130項目・11レポート・ページ・メニューまで一度に作られます。

#### 設計方針：Creator 側の項目はすべて text / textarea / number

ルックアップや選択肢（ドロップダウン）を一切使っていません。関係は ID を文字列で持ち、
日付・金額・真偽値も文字列／数値で保存して、**意味づけはウィジェット側が担当**します。

| 利点 | 内容 |
|---|---|
| 取り込みが確実 | 実績のある3つの型しか使わないため、パーサに弾かれにくい |
| 順序に依存しない | ルックアップの参照先を先に作る必要がない |
| 型崩れが起きない | 選択肢の値ずれ、日付書式の食い違いが原理的に発生しない |
| 移植しやすい | 同じ JSON を別の基盤に載せ替えられる |

真偽値は `"true"` / `"false"` の文字列で保存され、読み込み時にウィジェットが真偽値へ戻します。

#### .ds が使えない場合の保険

`ds/import_csv/` に、フォームごとの取り込み用 CSV を番号順で入れてあります。
列見出しがそのままフィールドのリンク名になります。`ds/forms_fields.csv` は全130項目の一覧です。

#### アプリ名について

### 6. 権限（ロール）を設定

権限は **2種類だけ** です。中間の権限は作りません。
「この人はどこまでさわれるのか」を、誰でも一言で言えるようにするためです。

| 権限 | できること | できないこと |
|---|---|---|
| **一般** | 申請する／承認する／自分の申請と、自分が承認に関わる申請を見る／同じ部署の下位者の申請を見る（機微度Sを除く）／自分の申請を誰が見たかを見る | 社員・部署・取引先・勘定科目の編集、承認経路の編集、申請区分の追加、全社の申請の検索、経理処理、全社の閲覧証跡 |
| **システム管理者** | すべての閲覧と編集 | （制限なし。ただし操作はすべて証跡に残る） |

経理担当・人事担当に全社の申請を見せる必要がある場合は、その人をシステム管理者にしてください。

Creator 側のロール設定：

| 権限 | Wf_Request_Form | Wf_Access_Form | 備考 |
|---|---|---|---|
| 一般 | 自分の申請＋自分が経路上にいる申請 | 追加のみ／閲覧は自分の申請に対するもの | |
| システム管理者 | 全件 | 追加＋閲覧 | **編集・削除は誰にも与えない** |

#### システム管理者だけパスワードを求めます

ポータルにログインした時点で本人確認は Zoho が済ませていますが、
システム管理者が管理画面（設定・マスタ／承認経路／経理処理／全社検索）に入るときだけ、
もう一度パスワードを入力させます。共有端末を開きっぱなしにしたまま、
別の人が元データや承認経路をさわるのを防ぐためです。

- 最初のログイン時に、本人がパスワードを決めます（8文字以上・英数字混在）
- 同じ画面を開いている間は再入力を求めません。再読込すると再度求めます
- 誤入力は回数とともに閲覧証跡に「アクセス拒否」として残ります
- パスワードを入れずに「一般利用者として使う」を選べます。
  その間は管理メニューが消え、URL を直接叩いても開けません
- 忘れたときは、**別のシステム管理者**が社員マスタの本人の画面から解除します
  （解除も証跡に残ります）。管理者が1人しかいない状態を避けるため、
  セットアップの進捗では「管理者を2人以上にする」を促しています

> パスワードは `admin_pass`（SHA-256ハッシュ）と `admin_salt`（乱数）に分けて保存します。
> 平文は保存しません。**これはログインの代わりではなく、管理画面の鍵です。**
> 本人確認そのものは、引き続き Zoho のポータルログインが担います。

`Wf_File_Form`（添付）は、申請と同じ条件で閲覧を制限してください。添付は申請本体より機微です。

レコードレベルの条件式（Creator の権限設定）：
```
Applicant == zoho.loginuser の社員レコード
|| ID in (Approvals[Approver == 自分].Request)
```

> **重要**：widget 側の権限制御（`Perm` モジュール）は「画面の親切」です。
> 守りは Creator 側のロールとレコードレベル条件で必ず二重にかけてください。

## 本人確認となりすまし防止

Creator 接続時は、`zoho.loginuser`（サーバーが保証するログインID）と社員マスタの `email` の
一致**だけ**を信用します。次の場合はデータを読み込まずに停止し、アクセス拒否として記録します。

- ログインIDが社員マスタに無い
- `is_active` が `false`（退職者など）

右上のユーザー切替は、**システム管理者のときだけ表示**されます。一般利用者には氏名が表示されるだけで、
他人になりすますことはできません（デモモードでは全員切替できます）。
切替中は画面に「◯◯として表示中（閲覧のみ）」と出て、申請・承認・マスタ編集は止まります。

ログイン後の最初の画面は **マイページ** です。自分の承認待ちと自分の申請がまとまっています。

## 動作モード

widget は起動時に Creator SDK の有無を判定します。

- **接続時** — Creator のレポートを読み書きします（サイドバー下部に「Zoho Creator 接続済」）
- **未接続時** — デモモードで起動し、localStorage 上の疑似データで全機能が動きます

ローカルで `widget/widget.html` をブラウザで開くだけでデモが動くので、
Creator にアップロードする前に画面を確認できます（初回は SDK 判定に約6秒かかります）。
